## 状态机设计

### 状态定义
```go
StateStandby  // 待命状态 - 初始状态，等待用户指令
StateSearch   // 搜索状态 - 执行搜索任务
StateFocus    // 专注状态 - 专注阅读搜索结果
StateExcited  // 兴奋状态 - 发现有用信息
StateOrganize // 整理状态 - 整理分类信息
StateDeliver  // 交付状态 - 交付整理结果
StateThink    // 思考状态 - 思考如何回答问题
```

### 状态转换规则
```
待命态 (standby)  → 搜索态 (search)    : 用户请求搜索
待命态 (standby)  → 思考态 (think)    : 用户请求思考

搜索态 (search)   → 专注态 (focus)    : 开始阅读结果
搜索态 (search)   → 兴奋态 (exciting) : 发现重要信息
搜索态 (search)   → 待命态 (standby)  : 搜索完成或取消

专注态 (focus)    → 兴奋态 (exciting) : 发现关键信息
专注态 (focus)    → 整理态 (organize) : 阅读完成，开始整理
专注态 (focus)    → 待命态 (standby)  : 中断或完成

兴奋态 (exciting) → 整理态 (organize) : 开始整理发现的信息
兴奋态 (exciting) → 专注态 (focus)    : 继续阅读其他信息
兴奋态 (exciting) → 待命态 (standby)  : 完成

整理态 (organize) → 交付态 (deliver)  : 整理完成，准备交付
整理态 (organize) → 待命态 (standby)  : 中断整理

交付态 (deliver)  → 待命态 (standby)  : 交付完成
交付态 (deliver)  → 思考态 (think)    : 用户需要进一步思考

思考态 (think)    → 待命态 (standby)  : 思考完成
```

## 动作系统设计

### 动作接口
```go
type Action interface {
    Name() string              // 动作名称
    Description() string       // 动作描述
    TriggerKeywords() []string // 触发关键词
    Emotion() string           // 情感状态
}
```

### 具体动作实现

| 动作名称 | 触发关键词 | 情感 | 描述 |
|---------|-----------|------|------|
| search | 搜索, 查找, 查一下 | 专注 | 小龙虾开始执行搜索任务，切换为「出发」动作 |
| focus | 专注, 认真, 仔细 | 专注 | 小龙虾动作从「翻找」逐渐变为「专注阅读」 |
| excited | 有用, 发现, 宝贝 | 兴奋 | 小龙虾突然兴奋起来，切换为「发现宝贝」动作 |
| organize | 整理, 分类, 汇总 | 认真 | 小龙虾切换为「整理资料」状态 |
| deliver | 好了, 完成, 给你 | 郑重 | 小龙虾切换为「郑重交付」动作 |
| think | 思考, 想想, 怎么答 | 思考 | 小龙虾进入「思考模式」，动作切换为「托腮」 |
| standby | 待命, 安静, 休息 | 安静 | 小龙虾切换为「安静待命」动作 |

### 动作匹配算法
1. 用户消息预处理（小写化、去除空格）
2. 遍历所有动作的触发关键词
3. 使用前缀匹配检查消息是否包含关键词
4. 返回所有匹配的动作
5. 按匹配度排序（未来可扩展）

## 数据流设计

### 用户消息处理流程
```
1. 用户发送消息 → POST /api/v1/message
2. API 层验证参数 → 调用服务层
3. 服务层处理消息:
   a. 更新最后活动时间
   b. 关键词匹配查找动作
   c. 根据消息内容决定状态转换
   d. 尝试状态转换
   e. 返回匹配动作和建议
4. 返回 JSON 响应给用户
```

### 搜索任务流程
```
1. 用户触发搜索 → POST /api/v1/search
2. 服务层处理:
   a. 转换到搜索状态
   b. 设置搜索动作
   c. 模拟搜索过程（硬编码）
   d. 返回搜索进度信息
3. 前端根据动作描述显示相应动画
```

## 并发安全设计

### 读写锁保护
```go
type ShrimpService struct {
    stateMachine   *state.Machine
    actionRegistry *action.Registry
    mu             sync.RWMutex  // 读写锁保护共享状态
}
```

### 锁使用策略
- **读操作**: 使用 `RLock()` - 允许多个并发读
- **写操作**: 使用 `Lock()` - 保证互斥访问
- **避免死锁**: 确保锁的获取和释放成对出现

## 性能考虑

### 内存优化
- 动作对象复用，避免重复创建
- 使用指针传递，减少拷贝
- 状态机轻量级设计

### 响应时间
- API 响应时间 < 100ms
- 动作匹配算法 O(n) 复杂度
- 状态转换 O(1) 复杂度
